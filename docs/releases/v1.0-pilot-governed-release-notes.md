## Summary

VITRAS v1.0-pilot-governed is the first formally frozen baseline of the VITRAS primary healthcare platform (UBS). It incorporates eight development sprints of security hardening, operational resilience, multi-tenant isolation, observability, governance tooling, and regulatory compliance scaffolding. This version is authorized for a controlled pilot deployment at 1–2 UBS facilities.

All Sprint 4.1 hotfixes have been QA-validated. The system is production-ready for a supervised pilot with the constraints documented in this release.

## What Changed From Initial State

The initial system was a single-UBS prototype without production hardening. This release represents the cumulative result of:

1. **Sprint 0–1:** Pilot readiness — safe prune, CPF race condition fix, file-mode filter parity, rate limit key correction
2. **Sprint 2–2.1:** Observability layer — JSON structured logs, CPF/CNS database uniqueness constraints, HMAC hash index, CloudWatch documentation
3. **Sprint 3–3.1:** Post-pilot hardening — migrations before listen, key separation, audit chain verification, snapshots, schema validation, health readiness gate
4. **Sprint 4:** Enterprise operations — /readyz, degraded mode, Redis circuit breaker, governance reports, unit bootstrap, LGPD/CFM documentation, security operations runbook
5. **Sprint 4.1:** Baseline freeze hotfixes — 7 targeted fixes for operational correctness before controlled rollout

## Security Highlights

### HMAC Hash Uniqueness (Sprints 2–2.1)
CPF and CNS identifiers are stored only as HMAC-SHA256 hashes using `PATIENT_LOOKUP_HASH_KEY`. Database unique constraints on hash columns prevent duplicate registrations. Raw identifiers never persisted in the database.

### SELECT FOR UPDATE (Sprint 1)
CPF registration race conditions eliminated via pessimistic row locking on lookup operations.

### Audit Chain Integrity (Sprint 3)
Every audit log entry is hash-chained to its predecessor. Chain verification endpoint detects tampering or orphaned entries. Startup validates chain integrity on boot.

### Rate Limit Fail-Closed (Sprint 2)
Upstash Redis rate limiting is fail-closed: if Redis is unavailable, all requests return 503 rather than bypassing limits. The circuit breaker with HALF_OPEN recovery prevents permanent lockout.

### Startup Hardening (Sprint 3)
HTTP server does not bind until all migrations complete. Fatal boot failure if critical migration 006 is missing in production. Warming phase delays health check green status until system is ready.

### Multi-Tenant Isolation (Sprint 4 — Unit Bootstrap)
Every patient, appointment, and clinical record is scoped to a `unitId`. Gestor role is restricted to their own unit. Unit bootstrap creates the isolation boundary at onboarding time. Cross-tenant access is architecturally prevented by scoped queries.

### adminRouter Ordering (Sprint 4.1 — S10-03)
`adminRouter` is now registered after the global `requireAuth` middleware, ensuring all admin routes inherit the global authentication gate in addition to their inline checks.

## Operational Highlights

### /readyz and /health (Sprint 4)
- `GET /readyz` — machine-readable readiness (200 = ready, 503 = not ready). Used by load balancers and deployment scripts.
- `GET /health` — subsystem status (postgres, redis, auditChain, migrations, startup phase, degraded reason).

### Circuit Breaker (Sprint 4 — S5-01 fixed in 4.1)
Redis/Upstash unavailability triggers a circuit breaker (OPEN → HALF_OPEN → CLOSED). HALF_OPEN probe failure now correctly reopens the circuit (S5-01 fix). State is logged as structured metrics for CloudWatch.

### Degraded Mode and clearDegraded (Sprint 4.1)
The system can enter degraded mode on non-fatal startup errors. `POST /admin/system/clear-degraded` (break_glass_admin or security_auditor) clears the flag once the root cause is resolved without requiring a restart.

### Structured Metrics (Sprint 4)
All significant events emit structured JSON metrics: `request_completed`, `auth_failure`, `deadlock_retry`, `rate_limit_hit`, `db_write_duration_ms`, `circuit_breaker_*`, `backup.health_warning`. CloudWatch dashboard queries documented in `docs/cloudwatch-dashboard.md`.

## Governance Highlights

### Governance Reports (Sprint 4)
Operational reports available to `security_auditor` role:
- `GET /admin/governance/reports/patient-access` — patient access patterns
- `GET /admin/governance/reports/auth-failures` — authentication failure analysis
- `GET /admin/governance/reports/activity` — system activity summary
- `GET /admin/governance/reports/audit` — audit log report (sorted by recency — S4-03 fix)

### Unit Bootstrap (Sprint 4)
`POST /admin/units/bootstrap` creates the foundational data structures for a new UBS unit (gestor account, default team, unit record) in a single atomic operation. S7-01 fix ensures the operation aborts cleanly if gestor is not found during mutation.

### Anonymization Pre-Flight Audit (Sprint 4.1 — S8-02)
Patient anonymization (`POST /admin/patients/:id/anonymize`) now executes the pre-flight compliance audit in a separate database transaction before the destructive anonymization begins. This creates a forensic record of the decision independent of whether anonymization succeeds.

## Upgrade Notes

### Required Environment Variables (Production)
| Variable | Requirement | Notes |
|----------|-------------|-------|
| `DATABASE_URL` | REQUIRED | PostgreSQL RDS connection string |
| `PATIENT_LOOKUP_HASH_KEY` | REQUIRED | ≥32 chars, separate from DATA_ENCRYPTION_KEY |
| `JWT_SECRET` | REQUIRED | ≥32 chars |
| `FRONTEND_ORIGINS` | REQUIRED | Production domain(s), comma-separated |
| `DATA_ENCRYPTION_KEY` | REQUIRED | ≥32 chars |
| `UPSTASH_REDIS_REST_URL` | RECOMMENDED | Rate limiting; if absent, runs without Redis rate limits |
| `UPSTASH_REDIS_REST_TOKEN` | RECOMMENDED | Required if UPSTASH_REDIS_REST_URL set |

### Required Migrations
All 8 migrations (001–008) must be present in `schema_migrations` table post-deploy. The system verifies this on startup and fails fatally if critical migration 006 is absent in production mode.

### Verification Steps After Deploy
1. `GET /readyz` returns 200
2. `GET /health` shows `postgres: ok`
3. `schema_migrations` table contains rows 001–008
4. `POST /admin/units/bootstrap` completes for the first UBS
5. Gestor account created with correct `unitId`
